## 14. Additional notes

1. **Sanity entry point for debugging**: immediately after `create_agent` Studio makes the exact sequence of calls documented in [§8.1.1](08.01-initialization.md) (common contract / sequence). Observing those in order is the shortest way to confirm that the ABI is wired correctly.
2. `QueueOnMainFn` ([§8.2.2](08.02-callbacks.md)) is the plugin's only safe path onto Studio's GUI thread (`CallAfter`). Studio's own inbound callback lambdas already marshal with `CallAfter` / `wxQueueEvent` — that does **not** replace `queue_on_main` for work the **plugin** initiates. wxWidgets is not thread-safe.
3. **Certificate files (`set_cert_file`)** — full detail in [§10.6](10.06-lan-tls-and-access-codes.md) / [§8.1.8](08.01-initialization.md). Studio passes `(<resources>/cert, slicer_base64.cer)`; both `slicer_base64.cer` (cloud) and `printer.cer` (BBL CA bundle) live in that folder. Stock plugin LAN trust behaviour is not documented here beyond the printer-side TLS observations in [§10.6](10.06-lan-tls-and-access-codes.md) / [§8.1.8](08.01-initialization.md).
4. **ABI/STL compatibility** is the single biggest foot-gun of this contract: the plugin has to be built with the exact same toolchain that built Bambu Studio (matching MSVC runtime on Windows, matching libstdc++ ABI on Linux, matching Xcode/libc++ on macOS). Any mismatch is undefined behaviour the moment a `std::string` / `std::map` crosses the library boundary.
5. **Static JSON key optionality (stock library).** A static classification of the stock library's JSON keys analysed **103 keys → 48 required** (all access sites at outer brace depth), **35 optional** (only inside control-flow blocks), **20 mixed**. The per-key table lives upstream at `output/unpacking/json_keys_optionality.tsv` (not vendored here). Cross-cutting observation, so it lives on this notes page rather than a single ABI chapter.

   Source: INTERESTING_REPOS.md cross-check #12 (baltobu docs, Frix-x/baltobu-reverse-networking, MIT)
6. **External recovery-method note (their method, for reference).** When we need off-LAN capture decryption, baltobu's live TLS method is worth reusing: anchor on the ServerHello `session_id` inside a minidump of the live client and scan ±16 KB around it for the adjacent 48-byte `master_key`, verify the candidate by GCM-decrypting the client `Finished` record (TLS 1.2 PRF-SHA384, 72-byte key block), then emit `CLIENT_RANDOM` and decrypt the stream; to prove channel content without touching TLS at all they heap-read the decrypted cloud `push_status` JSON straight from the process dump, showing both MQTT channels carry plain JSON. Marked as their method (docs 23/31), not an adopted tool. Version caveat: their docs 23/31 method assumes TLS 1.2 key schedule, while their docs/32 separately states the **cloud** broker is TLS 1.3 — an internal inconsistency on their side (1.3 has no `session_id`-derived master secret), unresolved; treat the method as TLS 1.2-local-channel only until verified. Source: `INTERESTING_REPOS.md` cross-check #18 (baltobu docs/23+31 vs 32, Frix-x/baltobu-reverse-networking, MIT).
